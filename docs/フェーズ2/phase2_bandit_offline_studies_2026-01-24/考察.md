# Phase 2 オフライン検証（Bandit導入前）考察メモ

## 1. 目的
- Safe-UCB導入に向けて、報酬モデル/制約モデルの妥当性と、環境シフト時の破綻（違反率の跳ね）を**オフラインで安全に**確認する。
- まずは非コンテキスト（context=0.5固定）の最小構成で、挙動の「型」を掴む。

## 2. 前提（定義・設定）
- 生成スクリプト: `scripts/phase2_offline_eval/run_offline_studies.py`
- 出力: `results/phase2_offline_studies_2026-01-24_v01/`
- Bandit設定
  - horizon: T=1000, reps=100, seed=0xD4B40201（スクリプト引数）
  - 制約: Pout(τ) ≤ ε（τ=1.0s, ε=0.10 は `docs/フェーズ2/Phase2_MVP仕様書_2026-01-21.md` に準拠）
  - 注意: `Fixed-CCS` は context 固定のため、「Phase1のCCS制御の再現」ではなく**ベースラインの形だけ**を見ている。
- 報酬モデル（現状）
  - `scripts/phase2_offline_eval/models/reward_model.py`
  - 定義: r(a) = -μC(a), μC(a) = (E_on(a)-E_off)/N_adv(a) [μJ/adv]
  - 参照: `results/deltae_v3rig_sweep_2026-01-21_v02_stats_ci.csv`, `results/deltae_v3rig_sweep_2026-01-21_v02_trials.csv`
- 制約モデル（現状）
  - `scripts/phase2_offline_eval/models/constraint_model.py`
  - 定義: g(a)=Pout(τ|a)=Pr[TL>τ]
  - データソースは env ごとに切替（表/ログから Pout を推定）

## 3. 主結果（今回の“型”）
出典: `results/phase2_offline_studies_2026-01-24_v01/sim_summary.csv`

- E2（actions={500,1000,2000}, cold）
  - `Safe-UCB` / `UCB` は violation_rate_mean が 0.07% 程度でほぼ同等、`Fixed-CCS` は 11% 程度。
  - `Oracle` が 0% なのは「安全集合が実質1点」に近い構造のため（後述）。
- E2（actions={500,1000,2000}, warm-start）
  - in-domain の warm-start は `safe_ucb_warm` が `Oracle` と同等まで張り付く。
  - E1→E2 の warm-start でも同様に張り付く（今回の報酬/制約の組合せでは、E1の事前知識が危険側へ誘導しにくい）。
- scan70（actions={100,500}, cold/warm）
  - `Oracle` でも violation_rate_mean が 2%台で残る（「100msでもPout(1s)>0」が効く）。
  - warm-start は「最初の危険行動（500ms）を引く回数」を減らす方向には効くが、今回は差が小さい。

## 4. 解釈（なぜこうなったか）
出典: `results/phase2_offline_studies_2026-01-24_v01/tradeoff_table.csv`

- **安全集合が“ほぼ1点”になりやすい**
  - E2 fixed では Pout(1s) が 500ms=0.000, 1000ms=0.111, 2000ms=0.556 なので、ε=0.10 では「500msのみが安全」になりやすい。
  - scan70（{100,500}）でも 500ms が明確に危険寄りで、実質的に「100msを選び続ける」問題に近い。
- **Safe-UCBとUCBの差が出にくい**
  - 上の構造だと、どちらも結局は最短で安全側に収束し、差分は「初期探索で危険腕を何回だけ引くか」に縮む。
  - 今回のE2では 1000/2000 を“初回に1回ずつ”引く期待違反回数（≈0.111+0.556）に整合する程度の差しか出ない。
- **warm-startが強すぎる（=Oracle化しやすい）**
  - warm-start は「同じ推定モデルの平均値」を初期値に入れているので、in-domain では Oracle に張り付くのが自然。
  - 環境シフトの評価としては“上限ケース”になりやすく、破綻（違反跳ね）を引き出しにくい。
- **Fixed-CCSの違反率が高いのは仕様**
  - context=0.5 固定で、実装上は「中間腕を選ぶ」挙動になりやすい（`scripts/phase2_offline_eval/models/safe_ucb.py`）。
  - これは「CCS制御が悪い」という主張には直結しない（ベースライン用途の確認）。

## 5. 妥当性チェック（split）
出典: `results/phase2_offline_studies_2026-01-24_v01/validity_reward_split.csv`, `results/phase2_offline_studies_2026-01-24_v01/validity_constraint_e2_split.csv`

- 報酬（μC）の split では、actionごとの test MAE が 2000〜2600 μJ/adv 程度で、分散が大きい（特に100msは相対誤差が効きやすい）。
- 制約（E2, 1000ms）は n=5 と小さく、train/test の平均で ε=0.10 を跨いで safe 判定が反転しうる（= safe set 推定が不安定）。

## 6. 限界（この結果の“守備範囲”）
- 報酬が μJ/adv なので、「広告回数を減らして省電力」の本筋（μJ/時間）と整合しない可能性がある。
- 制約は「固定間隔のTL/Pout推定」に依存し、動的制御（policy）の依存構造は表現していない。
- 乱数モデルは i.i.d. を仮定しており、時系列相関（連続欠落など）を持たない。

## 7. Next step（提案・優先度順）
推測で閾値を増やさず、既存データから導出できる範囲で進める。

1) 報酬定義の見直し（最優先）
- 候補: ΔE_total_mJ/60s や avg_power_mW を報酬にする（「間隔を長くして省電力」を直接反映）。
- 目的: “省電力側に寄りたい圧力”を作り、Safe-UCBの価値（安全を守りながら探索）を見える化する。
- 実装案: `scripts/phase2_offline_eval/models/reward_model.py` に `reward_mode` を追加し、`run_offline_studies.py` から切替できるようにする。

2) 環境シフトで破綻を引き出す
- 1) の報酬に切り替えた上で、E1→E2 で「安全集合の推定ズレ」が序盤違反に繋がるか（violation_rate の跳ね）を評価する。

3) 制約の不確かさを可視化/低減
- n が小さい action（例: E2 1000ms）で、PoutのCI/ブートストラップ幅を出して、safe 判定の不確実性を添える（主張の防御力が上がる）。
