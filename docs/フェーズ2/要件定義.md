# Phase 2 要件定義: QoS制約下の適応制御（モデルベース／不確実性考慮）

- 文書名: Phase 2 要件定義（QoS制約下の適応制御：モデルベース／不確実性考慮）
- 更新日: 2026-01-14
- 版: v2.1（文章化）
- 対象テーマ: QoS制約下におけるHAR不確実度に基づくBLEアドバタイジング間隔の適応制御
- 注意: 本Phaseは学習を前面に出さず、不確実性を考慮したモデル予測に基づく適応制御として記述する

## 1. Phase 2の目的と位置づけ

### 1.1 背景（送信側非観測(Blind TX)は前提）

- BLE Advertisingの一方向性により、TXはQoS（遅延・到達率）を直接観測できない
- Phase 2ではPhase 1の実測データから環境モデルを構築し、TX側が観測可能な文脈で適応制御を行う

### 1.2 Phase 2の狙い（主張の核）

- QoS制約（例: Pout(1s) ≤ ε）を明示的に扱いながら省電力性を改善する
- 未知の条件やrunでも破綻しないことを、形式的な汎化チェックで示す
- オンライン学習(Online learning)の強調は避け、不確実性考慮適応制御(Uncertainty-aware adaptive control)として記述する

## 3. 分割方針（ホールドアウト(Hold-out): リーク防止の必須要件）

### 3.1 stress_fixedの分割（n=1に適した形式）

- ランダム分割は禁止
- S1=train / S4=test のセッション分割を採用する

### 3.2 UCCSの分割（run単位）

- フェーズ内でのみ分割し、run単位のhold-outを基本とする
- D2bは run B=train / run B_02=test のように分ける
- nが小さいため、条件内 2/1 の分割を優先する

### 3.3 Context離散化境界の取り扱い

- U/S/CCSのQuantile境界はtrainのみで算出し固定する
- testに一切触れない

## 4. Phase 2で扱う制御問題の定義

### 4.1 観測可能量（TX側）

- HAR不確実度 U（0〜1）
- 安定度 S（0〜1）
- 合成指標 CCS（0〜1、Phase 1定義）
- これらから離散化してcontextを得る

### 4.2 行動（アドバタイジング間隔）

- Phase 2.1（最小構成）: {100, 500}
- Phase 2.2（拡張）: {100, 500, 1000, 2000}
- 開発リスク低減のため段階化し、要件書にも明記する

### 4.3 目的と制約

- 主目的: qevent（μC/event）を最小化
- 制約: Pout(1s) ≤ ε

## 5. 安全制約（安全集合(Safe Set)設計: アクションマスク(Action Masking)の改良）

### 5.1 基本方針

- アクションマスク(Action Masking)を主役にしない
- High-confidence Safe Set（高信頼安全集合）の中から行動を選ぶ
- 安全集合(Safe Set)が空の場合のみフォールバックする

### 5.2 安全判定（上側信頼境界）

- QoS制約: Pout(1s) ≤ ε_hard（例: ε_hard=0.1）
- 判定は点推定ではなく上側信頼境界で行う
- safe_actions = {a | Pout_upper(context, a; conf) ≤ ε_hard}
- フォールバック率は safe_set_empty_rate として診断指標に含める

## 6. 環境モデル（不確実性を持たせる）

### 6.1 Poutモデル（ベータ二項(Beta-Binomial)）

- 観測: pout_exceeded ∈ {0,1}
- 各 (context, action) にBeta事後（α, β）を持つ
- サンプルが少ないほど上側境界が高くなり、自然に保守的になる

### 6.2 qeventモデル（正規近似）

- 各 (context, action) に対してqeventの平均・分散を推定する
- 目的は省電力性の比較であり、必要に応じて条件平均の比較に寄せる

## 7. Context設計（比較と解釈性）

- CCS 3分割（ベースライン）: 解釈容易でPhase 1と接続しやすい
- (U, S) 3×3=9分割（本命）: CCSを介さない直接制御として位置づける

## 8. 評価設計（ログスコアリング）

- 自己参照を避け、log scoring（ログスコアリング）を中心に評価する
- trace-driven（トレース駆動）で挙動を可視化し、方策の差分を示す
- 図: ポリシーヒートマップ、制約遵守、qevent比較、フォールバック率

## 9. 指標（論文上の扱い）

- 主指標: qevent（μC/event）
- QoS制約: Pout(1s)
- 診断指標: safe_set_empty_rate, safe_actions_size
- 参考: tl_ms, pdr_unique, avg_power_mW

## 10. ログスキーマ（統合データセット）

- ファイル例: `bandit_dataset_{dataset}_{phase}_{run_id}.csv`
- dataset=stress_fixed/uccs, phase=D1等, run_id=B/B_02/run01等

**必須列**

- 識別子: dataset, phase, run_id, condition, split
- 時系列: step, t_ms
- 特徴: U, S, CCS
- 離散文脈: U_bin, S_bin, context_us, context_ccs
- 行動: action_ms, action_idx
- 指標: qevent_uC, pout_1s, pout_exceeded
- 監査: tl_ms, pdr_unique, avg_power_mW

## 11. 実装・論文化の要点

- Phase 2セクションは問題定義／モデル／安全集合(Safe Set)／評価設計／結果／限界で構成する
- stress_fixed n=1 の限界は明記し、形式検証として位置づける

## 12. リスクと対策

- stress_fixed n=1: 形式検証として扱い、検定は行わない
- 自己参照リスク: 評価はログスコアリングを主にする
- 安全集合(Safe Set)空振り: ε_hard と信頼係数(confidence)の感度分析を行う
- 行動集合4値との整合: Phase 2.1/2.2の段階化を文書に明記する
